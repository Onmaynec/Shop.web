# StandoffShop — TOTP и восстановление доступа

## Настройка

Войдите в `/account/security`, найдите раздел «Двухфакторная аутентификация», укажите текущий пароль. Система выдаст временный секрет. Добавьте его вручную в любое приложение, совместимое с TOTP (RFC 6238), затем подтвердите шестизначным кодом.

Настройка действительна 10 минут. После подтверждения будут выданы 8 резервных кодов. Сохраните их в менеджере паролей или в безопасном автономном хранилище. **После ухода со страницы эти коды больше не отображаются.**

После включения MFA все другие сессии пользователя отзываются. При следующем входе, помимо пароля, потребуется код из приложения или резервный код.

## Вход и резервные коды

- Одноразовый код TOTP действителен около 30 секунд; на сервере допустимо небольшое отклонение часов (один шаг).
- Подтверждённый код нельзя использовать дважды: последний успешно использованный временной шаг фиксируется атомарно.
- Резервный код работает однократно, после использования удаляется из базы. В интерфейсе отображается оставшееся количество, но не сами коды.
- Использование кодов ограничено общим rate limit попыток входа и дополнительных MFA-действий.
- При потере всех резервных кодов и устройства процесс автоматического восстановления недоступен. Не пытайтесь сбрасывать MFA напрямую в production-базе без установленной процедуры подтверждения личности.

## Для администратора

1. Сначала настройте MFA для всех аккаунтов с ролями ADMIN, SUPPORT и FULFILLMENT.
2. Сохраните текущий уникальный `SESSION_SECRET` в защищённом месте. Ротация без переноса TOTP-секретов требует повторной настройки факторов.
3. Только после этого задайте в `.env` строку `ENFORCE_STAFF_MFA=true`.
4. Перезапустите приложение, проверьте вход, страницы `/admin`, `/admin/support`, `/admin/queue` и API.
5. Отрицательная проверка: сотрудник без MFA при политике `true` не должен иметь привилегий, но может войти в кабинет и настроить MFA.

Политика безопасности реализована на сервере в `currentUser()`: незащищённая штатная сессия временно получает роль CUSTOMER для проверки прав. Настоящая роль в базе не изменяется и восстанавливается после включения MFA.

## Принципы хранения

- Секрет шифруется AES-256-GCM с произвольным уникальным IV, ключ выводится с разделением назначения из `SESSION_SECRET`.
- Резервные коды генерируются криптографическим источником и хранятся как HMAC-SHA256, а не открытым текстом.
- Тот же цифровой код TOTP нельзя использовать повторно после успешного подтверждения.
- Токены сессий остаются непрозрачными HttpOnly cookies; серверные сессии проверяются по БД.
- Настройка/выключение записываются в административный аудит без секретов и кодов.

## Известные ограничения

Защита от захвата учетных данных не гарантируется одним TOTP: нужны MFA для админов, reverse proxy, отдельная защита от фишинга, ограничение попыток, своевременные обновления зависимостей и независимая проверка. WebAuthn/passkeys, email-подтверждение и email recovery пока не реализованы.
