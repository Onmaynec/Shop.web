# StandoffShop v0.6.0 — безопасность

## Основные изменения

В этой версии серверные сессии хранятся в PostgreSQL. Старый формат cookie из v0.5.0 не поддерживается: все пользователи должны повторно войти после обновления. Никакие пароли или токены сессий не хранятся в базе в открытом виде.

- Токен сессии: случайные 32 байта; в cookie передаётся только токен, в БД хранится его HMAC-SHA256.
- Cookie: HttpOnly, SameSite=Lax, Secure в production, срок 7 дней.
- Сессии проверяются на каждом запросе: отзыв и истечение действуют немедленно.
- В профиле `/account/security`: просмотр до 30 действующих сессий, отзыв выбранной, завершение остальных и завершение всех.
- Смена пароля: проверка текущего, новый от 12 символов, отзыв всех сессий.
- Пароли: scrypt с уникальной случайной солью (сохранён формат совместимости с v0.5.0).

## Ограничение запросов

Счётчики `RateLimitBucket` находятся в PostgreSQL; инкремент выполняется атомарным UPSERT. После превышения возвращается `429` и `Retry-After`.

| Действие | Лимит |
| --- | --- |
| Вход в конкретный аккаунт | 10 попыток / 15 минут |
| Регистрация на конкретный email | 4 запроса / 24 часа |
| Создание новых заказов (аккаунт или email) | 20 запросов / час |
| Смена пароля | 5 запросов / час |
| Изменения через admin API | 120 запросов / 15 минут на администратора |
| Вход с одного IP, если настроен доверенный proxy | 60 попыток / 15 минут |
| Регистрация с одного IP, если настроен proxy | 15 запросов / час |
| Создание заказов с одного IP, если настроен proxy | 60 запросов / час |

Лимиты по email и аккаунту включены всегда. Лимиты по IP зависят от настройки `TRUST_PROXY_HEADERS`.

**Важно:** `TRUST_PROXY_HEADERS=true` разрешено только когда доверенный reverse proxy **полностью удаляет полученный от клиента X-Forwarded-For и устанавливает свой**. Нельзя включать эту настройку на приложении с прямым публичным доступом: заголовок можно подделать. Применять сетевые лимиты и правила доступа также рекомендуется на reverse proxy или WAF.

Повторы уже созданного заказа с тем же `Idempotency-Key` не расходуют лимит создания новых заказов.

## CSRF и HTTP-заголовки

Изменяющие запросы авторизации, аккаунта, заказов и админки проверяют `Origin` и `Host`. На защищённых маршрутах ожидается JSON. Сервер отправляет `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` и `Cross-Origin-Opener-Policy`.

Политика CSP пока не развёрнута: перед её включением нужна проверка nonce/SSR Next.js, внешних изображений и интеграций. Не добавляйте `unsafe-eval` в production ради устранения ошибок.

## Аудит

`AuditLog` хранит: администратора, действие, тип объекта, ID, минимальные безопасные детали и время. Записи для категорий, товаров, статусов заказов и инициируемых администратором sandbox-платежей сохраняются внутри соответствующей транзакции. В журнал **не передаются** пароли, токены, тела запросов или email покупателей.

Просмотр аудита: `/admin/audit`, только роль `ADMIN`.

Журнал предназначен для расследования действий сотрудников, но ещё не обеспечивает криптографически защищённую от изменений запись. В production необходимы отдельные права на БД, экспорт журналов в защищённое хранилище и контроль сроков хранения.

## Эквайринг

Реальные платежи НЕ подключены. Sandbox может работать только при `NODE_ENV !== production` и установленном отдельном `PAYMENT_SANDBOX_SECRET`; тестовый webhook проверяет подпись и повторные события. См. `docs/PAYMENTS.md`.

## Известные ограничения

Это ещё не результат полного security-аудита. Для публичного запуска нужны:
- Восстановление пароля через подтверждённый email и верификация адресов (без подключённого SMTP/провайдера письма не отправляются).
- Настроенный reverse proxy/WAF, ограничение размера тела запросов и соединений на сетевом уровне, защита от распределённого спама.
- MFA для администраторов, централизованный мониторинг, строгая CSP, сканирование зависимостей и секретов.
- Профилирование scrypt, нагрузочные и пентестовые проверки, регулярные обновления пакетов.
- Соблюдение законодательства о персональных данных и сроках хранения.

Утверждение, что магазин «полностью защищён», до этих действий некорректно.

## Дополнительные ограничения v0.9.0-rc.1

RBAC разделяет `ADMIN`, `SUPPORT`, `FULFILLMENT`, `CUSTOMER`; запрещено назначать чужие задачи исполнителю и читать чужую переписку покупателю. Выдача роли отзывает действующие сессии. CSV защищён от spreadsheet formula injection, но остаётся файлом с персональными данными.

Не закрыты: MFA для администрации, подтверждение email, recovery-процедура, защита на уровне WAF/reverse proxy, антивирусная проверка загружаемых файлов, production object storage, независимый аудит веб-приложения. Предрелиз не равнозначен разрешению принимать реальные платежи.
