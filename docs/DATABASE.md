# StandoffShop — миграции и резервное копирование (v0.6.0)

**Прочитайте перед запуском на существующей базе.** В v0.5.0 база обычно создавалась через `prisma db push` без `_prisma_migrations`. В v0.6.0 добавлены две версионированные миграции: baseline старой модели и новые таблицы безопасности.

## 1. Резервная копия на Windows

Остановите сервер Next.js, но оставьте Docker с PostgreSQL запущенным. В PowerShell из той же директории Compose-проекта, где находится существующая база:

```powershell
docker compose ps
powershell -ExecutionPolicy Bypass -File .\scripts\Backup-StandoffShop.ps1
```

Сценарий создаёт `pg_dump -Fc`, проверяет архив командой `pg_restore --list`, копирует его в `backups/` и проверяет, что файл не пуст. **Не публикуйте копии базы**, там персональные данные пользователей.

Восстановление необходимо проверять в **отдельной тестовой базе**. Никогда не запускайте восстановление поверх действующей базы магазина без проверенного плана.

При изменении каталога извлечённых файлов ZIP убедитесь, что используется тот же Docker Compose project name и тот же том PostgreSQL. Создание новой Compose-папки с другим именем часто приводит к созданию нового пустого тома.

## 2. Обновление существующей БД с v0.5.0

Этот порядок относится к базе, где уже существуют таблицы v0.5.0, но ещё нет таблиц `Session`, `RateLimitBucket` и `AuditLog`.

1. Сделайте и проверьте резервную копию.
2. Обновите исходники v0.6.0, выполните `npm install`, `npx prisma generate`.
3. **Только для старой базы** отметьте первоначальную миграцию применённой:

```cmd
npx prisma migrate resolve --applied 20261114000000_baseline
```

4. Примените изменения v0.6.0:

```cmd
npm run db:migrate
npx prisma migrate status
```

Команда `migrate deploy` создаёт только новые таблицы v0.6.0, не удаляя пользователей, товары и заказы.

**Не запускайте baseline SQL на существующей базе**: эти таблицы уже есть. `migrate resolve` только записывает факт применения baseline в историю миграций; поэтому перед ним важно проверить состояние старой схемы.

Если миграция уже применялась через `db push` и новые таблицы существуют, **не запускайте её повторно**. Сначала сравните структуру с миграцией и пометьте `20261114060000_security_stability` применённой через `migrate resolve --applied` только после проверки. При несовпадениях остановитесь и устраните расхождение.

## 3. Чистая установка

Если база ещё не содержит таблиц приложения:

```cmd
docker compose up -d
npm install
npx prisma generate
npm run db:migrate
npm run dev
```

Обе миграции применятся последовательно. Для демонстрационного каталога при необходимости выполните `npm run db:seed`.

`db:push` оставлена для экспериментальной разработки, но для обновления рабочих баз предпочтительнее `db:migrate`.

## 4. Ротация сессий

Формат cookie изменился в v0.6.0. Старые cookies перестанут давать доступ, пользователям потребуется войти повторно. `SESSION_SECRET` должен оставаться случайным, неизменным и недоступным третьим лицам: его замена инвалидирует новые сессии.

## 5. Уход за БД

Файл `scripts/cleanup-storage.sql` удаляет давно истёкшие счётчики и сессии. Запускайте его вручную после проверки срока хранения:

```cmd
docker compose exec -T postgres psql -U standoffshop -d standoffshop -f /dev/stdin < scripts/cleanup-storage.sql
```

Содержимое `AuditLog` и `PaymentEvent` автоматически не удаляется. Политика хранения и экспорт должны быть согласованы до production.

## 6. Проверки после обновления

```cmd
npx prisma migrate status
npm run typecheck
npm test
npm run build
```

После запуска сайта проверьте регистрацию/вход, завершение сессий, администратора, корзину, тестовый неоплаченный заказ и журнал аудита.
