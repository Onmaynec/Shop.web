# StandoffShop — платёжный контур v0.4.0

## Состояние

В v0.4.0 **реальный эквайринг не подключён**. Магазин умеет создавать неоплаченные заказы и содержит адаптер платежного провайдера, журнал событий и тестовую платёжную среду для локальной разработки.

Тестовые платежи не списывают деньги и не взаимодействуют с банками. Не подключайте sandbox к публичному адресу.

## Путь заказа

1. Покупатель формирует корзину и отправляет `POST /api/orders` с JSON и заголовком `Idempotency-Key`. Ключ создаётся браузером и сохраняется до успешного ответа.
2. Сервер проверяет Origin и структуру данных, заново загружает **активные** товары, рассчитывает сумму в копейках и сохраняет имена/цены позиций. Создаётся заказ `PENDING_PAYMENT`.
3. При повторе того же запроса с тем же ключом возвращается **тот же заказ** (HTTP 200); новый состав с тем же ключом отклоняется (HTTP 409).
4. В будущем внешний эквайринг создаст собственный платёжный идентификатор. `PaymentAttempt` связывает этот идентификатор с заказом, суммой и валютой.
5. Только после серверной проверки webhook и соответствия заказа/суммы/валюты событие `payment.succeeded` переводит `PENDING_PAYMENT → PAID`.
6. `payment.refunded` допускает только полный возврат подтверждённого платежа из `PAID`, `PROCESSING` либо `FULFILLED` в `REFUNDED`.

Ответ браузера, URL возврата после оплаты, ручной POST с суммой и кнопка на стороне клиента **не являются подтверждением оплаты**.

## Локальный sandbox

В файле `.env`:

```dotenv
PAYMENT_SANDBOX_ENABLED="true"
PAYMENT_SANDBOX_SECRET="YOUR_SEPARATE_RANDOM_SECRET_AT_LEAST_32_CHARS"
```

Сгенерировать секрет можно так:

```cmd
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Замените пример на сгенерированную строку. Не публикуйте `.env`. Отключите и повторно запустите сервер после изменения окружения.

Sandbox активен только когда одновременно выполнены условия:

- `NODE_ENV !== production`;
- `PAYMENT_SANDBOX_ENABLED=true`;
- `PAYMENT_SANDBOX_SECRET` длиной не меньше 32 символов.

Администратор может открыть `/admin/orders`, выбрать ожидающий заказ и нажать **SANDBOX · Оплатить (тест)**. Для подтверждённого тестового платежа доступна кнопка тестового полного возврата. Для этих действий нужна активная сессия роли `ADMIN` и корректный заголовок Origin.

**Даже если PAYMENT_SANDBOX_ENABLED=true в production, sandbox остаётся отключённым.** Endpoints симуляции и тестового webhook отвечают 404.

## Подписанный webhook

Тестовый endpoint: `POST /api/payments/webhooks/sandbox` (доступен только в локальном sandbox).

Заголовки:

- `x-ss-timestamp`: Unix-время в секундах;
- `x-ss-signature`: строка `sha256=<hex>`.

Подпись вычисляется как HMAC-SHA256 от `timestamp + "." + rawBody` с `PAYMENT_SANDBOX_SECRET`. Время допускает отклонение не более 300 секунд. Payload имеет строгую схему (eventId, type, provider, externalId, orderId, amountKopecks, currency). Сумма и валюта сравниваются с сохранённой платёжной попыткой и заказом.

После проверки событие сохраняется в `PaymentEvent`, уникальный ключ — `(provider, eventId)`. Запись события, обновление заказа и обновление попытки платежа проходят в **одной транзакции**. Повторная доставка того же события без изменения данных не меняет заказ. Некорректные переходы состояния отклоняются.

## Подключение реального эквайринга

Для внедрения нового провайдера потребуются отдельные действия, которых здесь пока нет:

1. Реализовать интерфейс `PaymentProvider` под документацию конкретной платёжной системы.
2. Надёжно хранить учётные данные поставщика только на сервере.
3. Создавать платёж у провайдера по сохранённой сумме заказа и фиксировать его ID.
4. Реализовать собственную серверную проверку webhook с реальной схемой подписи поставщика, обработкой таймаутов и повторных доставок.
5. Обрабатывать отказы, отмены, возвраты, редкие дубликаты и ошибочные суммы.
6. Добавить автоматическую выдачу **только после** подтверждения платежа, согласовать правила продажи и возвратов.
7. Провести тесты в тестовом кабинете провайдера и отдельный аудит безопасности.

Нельзя просто переименовать sandbox-провайдер в реальный: sandbox создан исключительно для локального тестирования. Частичные возвраты и автоисполнение в v0.4.0 отсутствуют.

## Проверки

- `npm test`: валидация, стабильность ключа заказа, подпись и срок действия webhook.
- GitHub Actions `verify`: Prisma → TypeScript → тесты → сборка → PostgreSQL smoke (в sandbox-отключённой production-сборке).
- GitHub Actions `sandbox`: PostgreSQL, dev-сервер, тестовая оплата, повторное webhook-событие, некорректная подпись, некорректная сумма, полный возврат.

## Ограничения перед запуском

Версия не предназначена для реальных платежей: пока нет ограничения частоты запросов/защиты от перебора паролей, восстановления аккаунта, контроля складских остатков, аудита действий сотрудников, юридических документов, очереди выдачи товаров и мониторинга webhooks. Эти задачи необходимо закрыть до коммерческого запуска.
