# StandoffShop — Order Management 2.0 (v0.8.0)

Обработка заказов теперь проходит через историю событий, очередь задач, внутренние комментарии и контролируемую выдачу цифровых файлов. **Реальный платёжный провайдер по-прежнему не подключён.**

## Обработка заказа

1. Покупатель добавляет товар в корзину. Сервер создаёт `PENDING_PAYMENT`, фиксирует стоимость/SKU и историю создания.
2. **Только доверенное подтверждение платёжного события** переводит заказ в `PAID`. Для разработки доступен sandbox, который всегда выключен в production.
3. При подтверждении оплаты создаётся **одна задача на позицию заказа**. Повторное платёжное событие не создаёт дубликаты.
4. Администратор видит задачи в `/admin/queue` или в карточке `/admin/orders`. Можно взять задачу, изменить состояние на `OPEN`, `IN_PROGRESS`, `BLOCKED` или `DONE`.
5. `PAID → PROCESSING` разрешён только при проверенном платеже. `PROCESSING → FULFILLED` — только если все задачи завершены.
6. В журнале `OrderActivity` сохраняются переходы статусов, действия сотрудников, сообщения, операции с материалами и события оплаты.
7. Если платёж возвращён, статус меняется на `REFUNDED`, незавершённые задачи блокируются, все опубликованные материалы отзываются.

**Нельзя** перевести заказ в `PAID` кнопкой админки или через браузер. Статус в БД без записи о подтверждённом платеже не даёт права на выполнение. Sandbox-события допускаются только в локальном dev-режиме и не открывают возможность продакшен-выдачи.

### Внутренние заметки и сообщения

В карточке заказа доступны два режима:
- **Только сотрудники** — запись для администраторов, не отображается покупателю.
- **Сообщение покупателю** — отображается в истории его заказа и создаёт уведомление внутри сайта, если заказ привязан к аккаунту.

Содержимое записей ограничено 2000 символами. Не размещайте в заметках пароли, данные платёжных карт и секреты.

### Уведомления

Покупатель с аккаунтом видит уведомления в `/account/notifications` и историю конкретного заказа в `/account/orders/<orderId>`. Прочтение отмечается только владельцем уведомления. События оплаты, статуса, публикации и отзыва материалов вызывают уведомления, если у заказа есть `userId`.

SMTP, push и внешняя отправка сообщений **не подключены**. Уведомления работают только внутри личного кабинета.

## Приватные файлы исполнения

- Сотрудник прикладывает файл к заказу `PAID` или `PROCESSING`. Предварительно сервер проверяет подтверждение оплаты.
- Допустимы PDF, PNG, JPEG и обычный TXT объёмом до **4 МиБ** с проверкой сигнатуры и типа.
- Файл сохраняется вне директории `public/` в `PRIVATE_DELIVERY_DIR` (по умолчанию `data/deliveries`).
- В БД хранятся метаданные: случайный `storageKey`, оригинальное имя, размер, MIME, SHA-256.
- При загрузке **выдача не происходит**. Нужно выполнить все задачи, перевести заказ в `FULFILLED` и отдельно нажать «Опубликовать» на файле.
- Скачивание через `/api/me/orders/<orderId>/downloads/<assetId>` проверяет владельца заказа по `userId`, статус `FULFILLED`, подтверждённый платёж, публикацию и отсутствие отзыва. SHA-256 перепроверяется при скачивании.
- Ответ всегда скачивается как attachment; заголовки запрещают кэширование и определение типа по содержимому.

**Гостевые заказы:** заказ без `userId` не имеет доступа к приватным файлам. Покупателю нужно оформить заказ из зарегистрированного аккаунта. Автоматической привязки старых гостевых заказов по совпадению email нет — это было бы небезопасно.

**Важное ограничение:** это файловое хранилище для локальной/self-hosted инсталляции, а не масштабируемый облачный storage. Отсутствуют объектное хранилище, антивирусное сканирование документов и автоматическое уничтожение невостребованных/отозванных файлов. В production используйте отдельный защищённый storage, лимиты reverse proxy и политику хранения.

### Резервное копирование

PostgreSQL хранит только метаданные. Резервное копирование `data/deliveries` или каталога, заданного в `PRIVATE_DELIVERY_DIR`, должно выполняться **отдельно от дампа базы**. Путь нельзя располагать под `public/`.

## Безопасность

- Административные запросы требуют серверной сессии ADMIN, проверки Origin, JSON и rate limit; multipart-upload дополнительно ограничивает размер.
- Клиенты не выбирают стоимость или статус оплаты: эти действия требуют серверной проверки.
- Транзакции базы гарантируют, что платёжные события, история и задачи фиксируются вместе.
- Изменения задач и операции выдачи блокируют строку заказа для предотвращения гонок с возвратами.
- Доступ к скачиванию не выдаётся на основании одного email, ID заказа или знания имени файла.
- Сообщения из внутренней истории никогда не включаются в публичный API и не отображаются в кабинете покупателя.

## Обновление базы с v0.7.0

Сначала остановите сайт, создайте дамп PostgreSQL и резервные копии `data/media` и `data/deliveries` (если уже существовала). Затем из прежней папки Docker Compose:

```cmd
docker compose up -d
npm ci
npx prisma generate
npm run db:migrate
npm run db:status
npm run dev
```

Новая миграция: `20261114080000_order_management`. Таблицы `OrderActivity`, `OrderTask`, `OrderDelivery`, `CustomerNotification` добавляются без удаления старых заказов, оплат и пользователей. Для старых заказов создаётся начальная запись истории, отражающая текущий статус на момент обновления.

Не удаляйте том PostgreSQL и не запускайте `docker compose down -v`.

## Тестирование

`npm test` — проверки ограничений файлов, статусов и санитарной обработки имён.

`npm run test:orders` — интеграционный сценарий требует запущенного сервера dev, PostgreSQL, включённого sandbox и отдельного тестового signing secret. Проверяет, что неоплаченный заказ не исполняется, задачи создаются один раз, внутренние заметки не видны покупателю, материалы недоступны до выполнения, скачивание привязано к владельцу, возврат отзывает файл.

Это версия для тестирования. До реальных продаж потребуется внешний эквайринг, подтверждение email, MFA, продакшен-storage, мониторинг и независимый security review.
